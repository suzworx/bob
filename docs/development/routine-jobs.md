# Routine jobs

The existing API process runs pg-boss **12.38.0** against the existing Postgres database. No additional service or credential is needed. Source was checked at released tag `12.38.0`, commit `2c1005b744952360e999c2000e155a1bfebb8951`, through GitHub CLI. Node must satisfy the package's >=22.12.0 requirement.

Apply `20261023020000_jobs.sql` before starting the updated API. It installs the pinned package's construction SQL (schema version 46), creates the single `routine-run` queue and grants a dedicated `bob_jobs` NOLOGIN role to `bob_server`. Runtime connections use the same URL with startup role `bob_jobs`. They have queue DML and invoker helper privileges, but no schema ownership, DDL, queue administration or account-table access. Browser roles have no schema usage. Existing domain handlers continue to use their separately injected account-scoped database.

`createRoutineJobQueue({ connectionString, handle })` returns `start`, `stop` and `send(runId)`. The run ID must be a UUID; it is both the sole payload field and the job ID. Repeated outbox handoff therefore returns the existing retained job without duplicating it. The outbox remains authoritative until send succeeds; feature run state must fence committed results because queue delivery is at least once and retained jobs eventually expire. Never treat a queue key as a permanent effect receipt.

The pool has at most two connections. One worker polls every two seconds, one job at a time. The queue allows two retries, beginning after 15 seconds with exponential backoff capped at 60 seconds. Heartbeats expire after 60 seconds and monitoring runs every 30 seconds. Jobs expire after 300 seconds; the handler receives cancellation combined with a five-minute deadline and shutdown. Shutdown aborts active handlers and gives the worker ten seconds to settle. Cancellation is cooperative: the Core handler must pass it to HTTP/model calls and fence its final write. A stale worker may continue remote work after losing its lease.

Runtime migration, schema creation, LISTEN/NOTIFY, cron scheduling, index rebuilding, queue-stat persistence and warning persistence are disabled. Completed/failed job retention is 24 hours. Queue payloads contain no account, mailbox or model content. Handler errors become the fixed `routine_execution_failed` error before pg-boss sees them. Driver errors emit only `v2.routine_queue_error` with fixed `queue_unavailable`; automatic pg-boss tracing and baggage propagation are disabled to prevent uncontrolled exception capture. Feature telemetry belongs at the Core boundary.

Local tests prove restricted-role startup and delivery, duplicate handoff, account/DDL/browser isolation, native queue transaction rollback, and stale-heartbeat reclamation to a bounded retry. A separate two-process test kills an active worker with SIGKILL and lets the second worker recover naturally, without clock manipulation. On 2026-10-23 it measured **78,284 ms recovery**, at most **four queue connections across two workers**, and **2 ms p95** over **399 concurrent database probes**. Evidence is generated at `data/routine-crash-proof.json` by `npx vitest run --config apps/api/vitest.db.config.ts apps/api/tests/platform/jobs/routine-crash.db.test.ts`. The database probe is not a chat/voice workload. Hosted pooling, network-partition fencing, sustained foreground voice/chat latency and real-account consent still require separate evidence.

API startup fails with a fixed `routine_queue_start_failed` error if the configured queue cannot start, allowing the host restart policy to recover instead of silently leaving schedules inactive. Apply both the queue migration above and `20261023030000_routine_runs.sql` before deploying the API.

API shutdown allows fifteen seconds overall, including the queue's ten-second drain. Module shutdown runs the existing outbox before the routine queue; routine dispatch clears its timer, drains its scan, then aborts active handlers and closes the queue pool.

For rollback, stop the queue worker and dispatcher while retaining the schema and authoritative run/outbox rows. Restarting the same pinned worker resumes pending jobs. Do not drop the schema to disable the feature. A future package upgrade requires separately reviewed migration SQL, local and hosted privilege checks, and an explicit mixed-version/recovery plan; runtime auto-migration stays disabled.
